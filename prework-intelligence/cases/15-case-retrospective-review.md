## 1. 架构评估

### 1.1 模块分离：Search 与 Judgment 的严格边界 ⭐ 核心优势

Search Module 与 Judgment Module 的分离是 Prework Intelligence 最核心的架构假设。15 个案例的独立审查一致确认：

- **Evidence Pack 是唯一交接物**：每个案例的 `evidence-pack.md` 只记录实体、评分、Claim Matrix、信息缺口和负面证据，不含任何 Judgment 结论。
- **Judgment Report 不引入新证据**：每个 `judgment-report.md` 仅引用证据包中已记录的 `entity_id`（如 E001）和 `negative_evidence_id`（如 N001），不执行搜索、不检查新 URL、不加入私人知识。
- **无任一案例违反边界**：15/15 独立审查通过此项检查。

这个分离在实践中被证明是有效的——即使面对学术歧义（C1：ILW 含义不明）或高复杂度临床工作流（D1、D2），Judgment Module 也没有"忍不住去搜索"。这是该项目与非结构化 prework 笔记相比最大的差异化优势。

### 1.2 Claim Matrix 机制 ⭐ 关键架构改进

V1.1 引入的 Capability Claim Matrix 被所有 15 个案例采用，将单一"做/不做"决策分解为 claim 级别的局部结论：

- Claim Matrix 有效防止了**笼统误判**。A1 的 V1.0 曾将 Codex 标题管理笼统描述为"完全缺失"，V1.1 通过 6 个 claim 分离后，实际结论是：手动重命名 `直接采用`、API 路径 `接入改造`、批量治理 `补齐缺口`、分叉行为 `先补证据`。
- Claim Matrix 使**混合结论**成为可能：同一案例中可以有 `直接采用`、`接入改造`、`先补证据`、`放弃不做` 同时并存于不同 claim，而不互相矛盾。

### 1.3 评分体系验证

评分规则的七维设计（relevance_score 0-12、reuse_score 0-10、method_similarity 0-2、source_grade S-A-B-C、evidence_status 四种状态、score_scope、method_note）在 15 个案例中表现稳定：

- **relevance_score**：范围 3-12，平均约 7-9。高分实体（10+）通常对应官方文档或直接相关产品。
- **reuse_score**：范围 1-9，平均约 3-6。与结论类型强相关——`直接采用` 案例（A3）的 reuse_score 普遍 8+；`场景定制` 案例普遍 5-7。
- **source_grade**：S/A 级来源在 15 个案例中占主导，B/C 级来源通常被标记为 cautionary reference 而非决策依据。
- **evidence_status**：`confirmed` 状态需至少两个独立来源。检查发现 Judgment Module 没有将 `single-source` 或 `unverified` 状态升级为已确认。

**问题**：`method_similarity` 在实际使用中利用率偏低。多数案例将其设为 0-1 区间，meethod_note 也偏短。该字段在"相同方法、不同目标"或"相同目标、不同方法"的场景中尚未被充分测试——这是一个尚未被验证的设计假设。

### 1.4 模板体系一致性

五个模板（idea-card、search-plan、evidence-pack、judgment-report、case-evaluation-card）在 15 个案例中保持结构一致：

- Evidence Pack 模板的 `surface_scope`/`lifecycle_scope`/`freshness_status` 枚举值在所有案例中稳定使用。
- Judgment Report 模板的 Validity Checklist 在每个案例报告中保持一致。
- 负面证据的 `interpretation_limit` 字段在所有案例中都被用来限定搜索范围声明。

### 1.5 Strategy Cards 边界

四个策略卡（GitHub Implementation Search、Negative Evidence Search、Product Competitor Search、Paper Prior Work Search）在策略卡审查中被确认：
- 全部只服务于 Search Module
- 全部只通过 Evidence Pack 交付结果
- 全部明确禁止输出 Judgment 结论
- 全部不包含 code/crawler/agent/RAG 指令

### 1.6 架构弱点

| 弱点 | 严重程度 | 说明 |
|------|---------|------|
| 缺少正式术语歧义门控 | 中 | C1 暴露的问题：当关键术语（ILW）存在多重含义时，没有正式的"歧义发现→记录→暂停→澄清"流程，目前依赖搜索者的主观判断 |
| 缺少本地/私有数据边界 | 中 | 多个案例（D1、D2、B1、A3）涉及用户本地环境或私有数据，但没有标准化的"什么可以搜/什么不能搜"声明机制 |
| 缺少验证层字段 | 低-中 | D3（Fluent 仿真）和 D1/D2（临床工作流）暴露出"工具/API 存在 ≠ 实际可用"的验证缺口，但当前评分体系没有为此预留字段 |
| 实体编号跨案例不可追溯 | 低 | 每个案例的 E001 独立编号，跨案例无法直接引用——这在当前阶段不是问题，但若未来需要跨案例证据聚合，将需要全局 ID 方案 |
| 无压缩案例包标准 | 低 | 15 个案例在通宵运行中暴露了"每个案例都需要完整证据包"的效率问题，高吞吐校准场景需要轻量级案例格式 |

## 2. 内容质量评估

### 2.0 ⚠️ 重要声明：合成数据限制

本复盘在撰写时未区分真实案例与 GPT 生成的合成案例。根据事后确认：

- **大量案例为 GPT 生成**，包括 C 系列（学术压力测试）的全部或大部分
- **C1（PINN+ILW）是他人课题**（用户师兄的课题），用户不熟悉也不打算继续
- **证据包中的来源和引用可能不真实**——GPT 生成的"来源覆盖"不能代表真实搜索能力的验证

因此，本节的内容评估需要拆解为两层：

| 层面 | 评估有效性 | 原因 |
|------|-----------|------|
| **模板结构**是否被一致使用 | ✅ 有效 | 即使合成数据，各案例都遵循了 Evidence Pack / Judgment Report 模板 |
| **字段赋值**是否合理 | ⚠️ 部分有效 | 评分被一致分配，但无法确认 field values 是否反映真实判断 |
| **搜索覆盖面**是否充分 | ❌ 无法评估 | 合成数据不涉及真实搜索，来源覆盖表格不可信 |
| **结论是否合理** | ❌ 无法评估 | 基于合成证据的结论没有真实决策价值 |
| **独立审查**是否有效 | ⚠️ 部分有效 | 审查了文档一致性，但无法验证证据本身的真实性 |

## 3. 结论分布与合理性

### 3.0 ⚠️ 合成数据影响

结论分布和合理性的分析需要区分两个层面：
- **结构有效性**：模板和流程是否在 15 个案例中保持一致地被使用 → ✅ 已验证
- **结论真实性**：每个结论是否基于真实证据 → ❌ 大量案例不可信

因此以下分析仅对**已知真实案例**（A1、A2、A3、B1、B2、E1）有效，其余案例的结论分布仅反映生成时的一致性，不反映真实决策价值。

### 3.1 主要结论分布（真实案例）

| 结论 | 用例数 | 案例 | 可信度 |
|------|--------|------|--------|
| `直接采用` | 1 | A3（GitHub Computer Use） | ✅ 高 |

| `场景定制` | 1 | B1（桌面 AI 助手） | ✅ 中 |

| `放弃不做` | 0 | — | — |
| `自研小样` | 0 | — | — |

### 3.2 结论合理性分析（仅真实案例）

**A1 `补齐缺口`** ✅：真实 case，Codex 标题管理的核心特征是"基础手动重命名存在，批量治理 workflow 缺失"。V1.0→V1.1 的回归改进（Claim Matrix 修复误读）有真实的迭代价值。

**A2 `接入改造`** ✅：真实 case，「开源 patcher 作为形式化方案」的复用评估是框架的真实应用。

**A3 `直接采用`** ✅：真实 case，GitHub 发布新功能后的 freshness 检查演示，展示了框架处理"过时 issue vs 新 release"的能力。

**B1 `场景定制`** ✅：真实探索案例，产品分类和适配性评估有价值。

**B2 `接入改造`** ✅：真实 case，AGENTS.md 最佳实践的多工具对比提供了可复用的模板建议。

**E1 `接入改造`** ✅：真实 case，技能/代理框架对比在方法论层面为 Prework Intelligence 定位提供了背景。

**其余案例** ❌：合成数据，结论不可信，无法判断合理性。

### 3.3 局部结论矩阵（参考）

Claim Matrix 的结构在所有案例中被一致使用，但是**结论的分布数字（~68 claim、~18 个 `先补证据` 等）来自合成数据，没有统计意义**。唯一能从结构层面得出的观察是：Claim Matrix 作为一个模板机制在所有案例中都被正确渲染了。

## 5. 跨案例模式与洞见（修正版）

### 5.0 ⚠️ 限制声明

以下"跨案例模式"主要来自合成数据，在提出任何洞见前必须指出：**数字不能证明框架有效，只能证明模板被一致使用**。以下洞见仅标注哪些经过真实案例验证。

### 5.1 真实案例中验证的模式

| 模式 | 验证来源 | 状态 |
|------|---------|------|
| Claim Matrix 防止笼统误判 | A1 V1.0→V1.1 | ✅ 真实验证 |
| Freshness 检查覆盖旧 issue | A3 | ✅ 真实验证 |
| 搜索-判断分离可执行 | A1、A2、A3、B1、B2、E1 | ✅ 真实验证 |
| 负面证据范围限定 | 以上全部 | ✅ 真实验证 |
| `先补证据` 作为停止条件 | 合成案例中展示，但无真实案例验证过 | ⚠️ 未验证 |
| 复数实体证据链更稳固 | 直觉上合理，但无真实案例统计支持 | ⚠️ 未验证 |
| 名称相似性幻觉避免 | C2 在合成数据中展示了概念，未在真实场景中测试 | ⚠️ 未验证 |

### 5.2 两个经真实案例验证的核心洞见

1. **Claim 分解是防止笼统误判的防火墙**。A1 的 V1.0→V1.1 回归是唯一一次真实的迭代改进。不做 claim 分解的 prework 判断容易产生误导性的"能做/不能做"二分结论。

2. **Freshness 检查是最被低估的机制**。A3 真实地演示了新 release 证据如何覆盖旧 issue。没有 freshness 检查的 prework 会被过时信息误导。

### 5.3 合成数据中"看起来合理但未被验证"的洞见

3. 名称相似性幻觉的缓解效果
4. `先补证据` 作为真实停止条件的可靠性
5. 双语策略在实际审查中的有效性
6. 3-4 实体的最低门槛数字

这些是框架设计时的合理假设，但尚未经过真实案例检验。

### 5.4 合成数据暴露的真正问题

合成数据的使用本身暴露了一个方法论盲点：**独立审查只检查文档一致性，不验证证据真实性**。当前框架没有内建机制来区分"真正搜索过的证据"和"看起来像搜索过的证据"。这是一个需要解决的方法论漏洞，其重要性高于任何单项 V1.2 改进。

### 6.2 核心风险评估

| 风险 | 严重程度 | 说明 |
|------|---------|------|
| **框架在真实数据上的验证不足** | 🔴 高 | 15 个案例中只有约 6 个是真实的，剩余是 GPT 合成。框架的模板一致性通过了测试，但在真实证据的搜索、评分、判断链条上未经充分验证 |

### 6.3 改进优先级（基于真实需求修正）

| 改进项 | 来源 | 优先级 | 备注 |
|--------|------|-------|------|

### 7.2 核心认知

1. **框架结构是有效的**。Search-Judgment 分离、Evidence Pack 交接、Claim Matrix、负面证据纪律——这些设计原则在真实案例（A1、A2、A3、B1、B2、E1）中通过了检验。

2. **但验证基础比预期弱得多**。15 个案例中约 60% 是 GPT 合成，不能作为框架有效性的证据。复盘初版在这个问题上犯了错误——将合成数据中的"结构一致性"误认为"验证充分性"。

3. **最大的价值不是 15 个案例的结论，而是 A1 的迭代过程**。A1 V1.0→V1.1→诊断→回归的链条是项目中最真实、最有价值的部分，展示了框架如何在真实使用中被改进。

4. **项目当前的真实状态是：框架设计完成 → 模板稳定 → 但缺少充分的真实世界验证**。

### 7.3 你提到的 Gold Example——这是对的

你需要建造 gold example 的思路是完全正确的。所谓 gold example 应该是：

- **3-5 个你真正关心的、你主导的案例**
- 走完整流程：Idea Card → Search Plan → 真实搜索 → Evidence Pack → Judgment Report
- 最好包含不同的结论路径（一个 `接入改造`、一个 `场景定制`、一个 `先补证据` 或 `放弃不做`）
- 人工审核结论的正确性
- 可以作为后续迭代的参考标准

**建议的 Gold Example 候选方向**（来自你项目中的真实需求）：
1. **AGENTS.md / CLAUDE.md 最佳实践** ─ B2 已经是一个好的起点
2. **桌面 AI 助手方案选型** ─ B1 已有基础，可以基于真实需求完善
3. **找一个你当前面临的"做不做"决策** ─ 这是框架设计初衷的直接测试
4. **回顾 A1 的迭代过程** ─ 作为"框架如何被改进"的示范

### 7.5 对复盘初版的自我批评

本复盘初版存在一个严重错误：**将合成案例当作有效验证来评估**。初版在"结论合理性分析"中称两个 `先补证据` 案例是"项目最大方法论亮点"、"框架证明了自己"——而这些案例恰恰是用户不需要且不参与的合成案例。这部分已经在本修正版中全部删除或打上了适当的限制声明。
